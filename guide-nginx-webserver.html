Nginx Web Server

Nginx installed on the spserver host — serving the spserver knowledge base from /var/www/dustyserver/ at dustyserver.co.in. Every config line explained, every file in the tree mapped, nothing left unexplained.

01 — What & Why
What a web server is — in plain English

A web server is a program that listens on a network port (usually port 80 for HTTP, 443 for HTTPS) and responds to requests. When a browser visits a URL, it sends an HTTP request to the server. The web server reads that request, finds the right file or service, and sends back a response.

Nginx (pronounced "engine-ex") is one of the two dominant web servers in the world (the other being Apache). It is known for being fast, memory-efficient, and capable of handling many simultaneous connections. On spserver it serves the knowledge base HTML files from disk and forwards other requests to Docker backends.

What happens when you visit dustyserver.co.in
1. Browser sends: GET / HTTP/1.1 to spserver's IP on port 80
2. Nginx receives the request
3. Nginx reads its config — finds the server block for dustyserver.co.in
4. Nginx looks for /var/www/dustyserver/index.html
5. Nginx sends the file contents back as an HTTP response
6. Browser renders the HTML
What Nginx does not do
Nginx does not execute application code — it serves files. If you put a Python script in /var/www/, Nginx will serve it as raw text, not run it. For dynamic applications (Flask, Node.js), Nginx forwards requests to the application and proxies the response — that is the reverse proxy role, covered in Phase 2.
02 — Two roles
Nginx as a web server vs as a reverse proxy

Nginx does both jobs on spserver — understanding which role applies where is important.

Role What Nginx does Used for on spserver
Web server this guide Reads files from disk and sends them to the browser. Nginx is the final destination — there is no backend application. Serving the knowledge base HTML files from /var/www/dustyserver/ at dustyserver.co.in
Reverse proxy Phase 2 Forwards requests to a backend application (Flask, Jenkins) and relays the response. Nginx is a middleman — the real work happens in the backend. Proxying jenkins.dustyserver.co.in → Jenkins on port 8090. Covered in guide-nginx-proxy.html.
ℹ The config syntax is the same for both roles — a server block with a server_name and a location block. The only difference is what's inside location: a root and try_files for static files, or a proxy_pass for a backend service.
03 — File structure
Every Nginx file and directory — what it is and what it does

Understanding the file layout before touching any config avoids a lot of confusion. Every path below is on the Ubuntu host — not inside a container.

/etc/nginx/
—
Root of all Nginx configuration. Every file Nginx reads lives here.
├──
nginx.conf
—
The master config file. Sets global settings (worker processes, log paths, connection limits). Includes all other config files. Do not put site configs here — use sites-available instead.
├──
sites-available/
—
Holds all site config files you have written. Files here are not active — Nginx doesn't read this directory directly. Think of it as a library of available configs.
│ ├──
dustyserver
—
The server block for dustyserver.co.in — serves the knowledge base HTML files. Written by us, symlinked to sites-enabled to activate it.
│ └──
default
—
The default site installed by Nginx — serves the "Welcome to nginx" page. Should be disabled (symlink removed from sites-enabled) once you have your own site.
├──
sites-enabled/
—
Contains symlinks to configs in sites-available. Nginx reads only this directory. A config is active if and only if a symlink to it exists here.
│ └──
dustyserver → ../sites-available/dustyserver
—
A symlink pointing to the dustyserver config. Creating this symlink is what activates the site. Removing it deactivates the site without deleting the config.
├──
conf.d/
—
An alternative location for config snippets — loaded automatically via a glob include in nginx.conf. Commonly used for upstream definitions and shared config. Less common than sites-available on Ubuntu.
├──
mime.types
—
Maps file extensions to MIME types. Tells Nginx to send Content-Type: text/html for .html files, image/png for .png files, etc. Included by nginx.conf. Rarely modified.
├──
snippets/
—
Reusable config fragments that can be included in server blocks. Certbot places its SSL config here (options-ssl-nginx.conf). Include with: include snippets/fastcgi-php.conf;
└──
modules-enabled/
—
Symlinks to compiled Nginx modules. Rarely touched manually — modules are enabled through apt packages (e.g. nginx-extras).
/var/log/nginx/
—
Nginx log files. The most important files for debugging.
├──
access.log
—
Every HTTP request Nginx handles — client IP, timestamp, request line, status code, response size. One line per request.
└──
error.log
—
Errors — failed connections, config problems, permission denials, upstream failures. Check this first when something doesn't work.
/var/www/
—
Convention: where web-served files live. Nginx runs as the www-data user, which has read access here. Put your HTML, CSS, images, and JS here.
└──
dustyserver/
—
The document root for dustyserver.co.in. Contains the knowledge base HTML files. Nginx serves files from here when a request matches the dustyserver server block.
ℹ Why /var/www/ and not /home/sipu/www/? The Linux Filesystem Hierarchy Standard (FHS) defines /var/www/ as the conventional location for web content. Nginx runs as the www-data system user. That user has read access to /var/www/ by default — it does not have access to home directories. Putting files in /home/ would require manually granting permissions.
01 — Master config
nginx.conf — the master config file, line by line

/etc/nginx/nginx.conf sets global behaviour for the entire Nginx process. It is not where you put site configs — site-specific configuration lives in sites-available/. The two files in the config below are the most important lines in the whole file.

The left column is the actual directive. The right column is what it means and why it is there.

Directive
What it does & why
Global context — top level, outside any block
user www-data;
Nginx worker processes run as this system user. www-data is a low-privilege user with no shell — a security measure. Files in /var/www/ must be readable by this user, or Nginx will return 403 Forbidden.
worker_processes auto;
auto tells Nginx to spawn one worker process per CPU core. Workers handle connections — more workers means more concurrent requests can be processed. auto is almost always correct; only change this if you have a specific reason.
pid /run/nginx.pid;
Nginx writes its master process ID to this file when it starts. systemd uses this file to track the process — it's how systemctl stop nginx knows which process to send the signal to. Don't change this.
include /etc/nginx/modules-enabled/*.conf;
Loads any compiled Nginx modules. These extend Nginx's capabilities (e.g. stream module for TCP proxying). Managed by apt packages — you rarely need to touch this.
events block — controls how workers handle connections
events {
  worker_connections 768;
}
worker_connections is the maximum number of simultaneous connections a single worker process can handle. Total max connections = worker_processes × worker_connections. 768 per worker is conservative but sufficient for a personal server. Increase if you see "worker_connections are not enough" in error.log.
http block — all web traffic settings
sendfile on;
Enables the sendfile() Linux system call to transfer files directly from disk to the network socket — bypassing the userspace buffer. This makes static file serving significantly faster. Always on.
tcp_nopush on;
Works with sendfile — buffers TCP packets and sends the HTTP response header and the beginning of the file body in a single packet instead of two. Reduces round trips and improves throughput on busy servers.
types_hash_max_size 2048;
Controls the size of the hash table Nginx builds from mime.types. A larger table speeds up MIME type lookups for files with many different extensions. 2048 is the default — sufficient for the standard mime.types file.
include /etc/nginx/mime.types;
Loads the MIME type mappings. Without this, Nginx would send every file as application/octet-stream — browsers wouldn't know to render HTML or display images. This file maps extensions like .html → text/html, .png → image/png.
default_type application/octet-stream;
The fallback MIME type for files not listed in mime.types. application/octet-stream tells the browser: "this is binary data — download it, don't try to render it." A safe default.
access_log /var/log/nginx/access.log;
Path for the access log — every request Nginx handles is logged here with client IP, timestamp, request, and status code. Can be overridden per server block to write to a different file per site.
error_log /var/log/nginx/error.log;
Path for the error log. This is the first place to look when something isn't working. Log level defaults to error — only errors are written. Change to error_log ... debug; for verbose troubleshooting (then set it back — debug logs are huge).
gzip on;
Compresses responses before sending them. HTML, CSS, and JS typically compress to 20–30% of their original size. Faster page loads for visitors, less bandwidth. The browser sends an Accept-Encoding: gzip header to signal it supports compression.
include /etc/nginx/conf.d/*.conf;
include /etc/nginx/sites-enabled/*;
These two lines are what connect sites-enabled to the master config. Every file in sites-enabled/ is loaded as part of the Nginx config. This is why creating a symlink in sites-enabled/ activates a site — nginx.conf automatically includes it on the next reload.
02 — Server block
The dustyserver server block — every line explained

A server block is the unit of configuration for a single website or service. Nginx can have many server blocks — each one handles a different domain. The server_name directive is how Nginx decides which block handles each incoming request.

This is the exact server block used for dustyserver.co.in on spserver. Not a single line is left unexplained.

Line
What it does & why
/etc/nginx/sites-available/dustyserver — full server block
server {
Opens the server block. Everything inside this block defines the configuration for one virtual host — one domain. Nginx can have many server blocks, one per site. The closing brace at the end of the file closes this block.
  listen 80;
80 is the standard port for HTTP. This tells Nginx to accept connections arriving on port 80. When a browser visits http://dustyserver.co.in, the browser connects to port 80 by default — this is the instruction that intercepts it. After Certbot runs, this line becomes a redirect to port 443.
  listen [::]:80;
Same as the line above but for IPv6. [::] is the IPv6 wildcard address — equivalent to 0.0.0.0 for IPv4. Both are needed so the site is reachable whether the visitor connects via IPv4 or IPv6.
  server_name dustyserver.co.in;
The domain name this block responds to. When a request arrives on port 80, Nginx reads the Host header of the HTTP request and compares it to all server_name values across all server blocks. The block with a matching server_name handles the request. This is how one Nginx can serve many different domains on the same IP.
  root /var/www/dustyserver;
The document root — the directory on disk where Nginx looks for files. When a browser requests /index.html, Nginx looks for the file at /var/www/dustyserver/index.html. When it requests /style.css, Nginx looks for /var/www/dustyserver/style.css. The URL path is appended to this root.
  index index.html index.htm;
When a request comes in for a directory (e.g. just / with no filename), Nginx tries these filenames in order and serves the first one it finds. So GET / becomes GET /index.html automatically. Both index.html and index.htm are listed as fallbacks — index.html is checked first.
  location / {
A location block matches incoming URL paths. / matches everything — it is the catch-all. More specific location blocks (e.g. location /api/) would take precedence over this one when a URL starts with /api/. For a simple static site, one location / block is all you need.
    try_files $uri $uri/ =404;
Nginx tries to serve the request in three steps in order: 1. $uri — look for a file at the exact URL path (e.g. /style.css). 2. $uri/ — look for a directory with that name and serve its index file. 3. =404 — if neither exists, return an HTTP 404 Not Found response. Without this, Nginx would return a confusing empty response for missing files.
  }
Closes the location block. Everything between the opening brace above and this closing brace applies only to URLs matching location /.
}
Closes the server block. Everything between the first opening brace and this closing brace defines the configuration for dustyserver.co.in.
ℹ Every directive inside a server block ends with a semicolon. Every opening brace { must have a matching closing brace }. These are the two most common causes of nginx -t failures — a missing semicolon or an unmatched brace.
03 — Enable / disable pattern
sites-available vs sites-enabled — why two directories

This two-directory pattern solves a specific problem: how do you have a config file ready to go but not yet active? You might want to write a site's config, test it, and only activate it when everything is correct — or temporarily disable a site without deleting its config.

/etc/nginx/sites-available/dustyserver
the real config file — always here
symlink
ln -s
↓
/etc/nginx/sites-enabled/dustyserver
a symlink pointing to the file above
nginx.conf
includes
↓
Nginx reads sites-enabled/* on startup and reload
→ site is active
Action
What it does & why
sudo ln -s /etc/nginx/sites-available/dustyserver
    /etc/nginx/sites-enabled/dustyserver
Enable a site. Creates a symlink (a pointer) in sites-enabled that points to the config in sites-available. Nginx reads sites-enabled/ and follows the symlink to read the actual config file. Only one copy of the config exists — the one in sites-available. The symlink is just a pointer. Edit sites-available and the change is immediately reflected through the symlink.
sudo rm /etc/nginx/sites-enabled/dustyserver
Disable a site. Removes only the symlink — the actual config in sites-available is untouched. After a reload, Nginx no longer reads this config and the site goes offline. To re-enable: recreate the symlink. This is far safer than editing or deleting the config file itself.
sudo rm /etc/nginx/sites-enabled/default
Disable the default site. The default site Nginx installs intercepts all requests that don't match any server_name. If it stays enabled, visitors to dustyserver.co.in might see the "Welcome to nginx" page instead of your content. Always disable it once your own site config is working.
⚠ Always use absolute paths in symlinks. sudo ln -s yserver /etc/nginx/sites-enabled/dustyserver — both paths absolute. A relative path like ../sites-available/dustyserver is resolved from the directory where you ran ln -s, not from sites-enabled/ — which usually gives you a broken symlink that silently does nothing.

02 — Serve a static page
Step 2 — Serve the spserver knowledge base
2
Create the document root and add files
▼

The document root is where Nginx looks for files to serve. We use /var/www/dustyserver/ — following the Linux convention for web files. The directory must exist and be readable by the www-data user.

bash
# Create the directory for dustyserver's web files
# -p creates parent directories if they don't exist
sudo mkdir -p /var/www/dustyserver

# Set ownership to the www-data user and group
# Nginx runs as www-data and must be able to read these files
sudo chown -R www-data:www-data /var/www/dustyserver

# Set permissions: owner can read/write, group and others can read
# 755 on directories: allows Nginx to list directory contents
# 644 on files: allows Nginx to read files, but not execute them
sudo chmod -R 755 /var/www/dustyserver

# Copy the knowledge base HTML files into the document root
# (adjust the source path to wherever your files are)
sudo cp -r ~/spserver-Knowledge-Base/* /var/www/dustyserver/

# Confirm the files are there
ls /var/www/dustyserver/
# index.html  style.css  guide-ubuntu.html  guide-ssh.html  ...
3
Write the server block config
▼

We write the config into sites-available first — it won't be active yet. We'll enable it with a symlink in the next step, after verifying the syntax.

bash
# Open a new config file in sites-available
sudo nano /etc/nginx/sites-available/dustyserver
/etc/nginx/sites-available/dustyserver
server {
    listen 80;               # accept HTTP connections on port 80
    listen [::]:80;          # same, for IPv6

    server_name dustyserver.co.in;  # only handle this domain

    root /var/www/dustyserver;      # serve files from this directory
    index index.html index.htm;     # serve index.html when / is requested

    location / {
        try_files $uri $uri/ =404; # serve file, or directory, or 404
    }
}
4
Enable the site, disable the default, test, and reload
▼
bash
# Enable the site by creating a symlink in sites-enabled
# Absolute paths only — relative paths produce broken symlinks
sudo ln -s /etc/nginx/sites-available/dustyserver /etc/nginx/sites-enabled/dustyserver

# Disable the default site — it would intercept requests that should go to dustyserver
sudo rm /etc/nginx/sites-enabled/default

# ALWAYS test the config before reloading
# A syntax error would leave Nginx in a broken state on restart
sudo nginx -t
# nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# nginx: configuration file /etc/nginx/nginx.conf test is successful
#
# If you see errors: fix the config, run nginx -t again before continuing

# Reload Nginx — applies the new config without dropping connections
sudo systemctl reload nginx

# Test locally using the Host header (before DNS is set up)
curl -H "Host: dustyserver.co.in" http://localhost/
# Should return the index.html content

# Once DNS is pointing to spserver — test with the real domain
curl http://dustyserver.co.in/
✓ If nginx -t reports "test is successful" and curl -H "Host: dustyserver.co.in" http://localhost/ returns your HTML — Nginx is correctly serving the site. Point the DNS A record at spserver's IP and the domain goes live.
01 — Commands
Essential Nginx commands — what each one does
Service management
sudo nginx -t
Test the entire Nginx config for syntax errors. Reports the exact file and line number of any error. Run this before every reload. Safe — does not touch the running Nginx process.
sudo nginx -T
Same as -t but also prints the full merged config to stdout. Useful to see exactly what Nginx will load — including all included files.
sudo systemctl reload nginx
Apply config changes gracefully. Existing connections finish serving — no requests are dropped. The correct way to apply config changes in production.
sudo nginx -s reload
Identical to systemctl reload nginx. Sends a reload signal directly to the Nginx master process. Both work — use whichever you prefer.
sudo systemctl restart nginx
Full stop and start. Drops all active connections briefly. Use only when reload is insufficient — e.g. after upgrading Nginx itself. Never use this in production without warning.
sudo systemctl status nginx
Show current state — running or stopped, PID, recent log lines. The first command to run when something isn't working.
sudo systemctl enable nginx
Configure Nginx to start automatically on boot. Creates a systemd symlink. Run once after installation.
sudo systemctl disable nginx
Remove the boot-start symlink. Nginx will no longer start on reboot. Does not stop a currently running Nginx.
Sites management
sudo ln -s /etc/nginx/sites-available/dustyserver /etc/nginx/sites-enabled/dustyserver
Enable a site. Creates a symlink — Nginx reads sites-enabled/ and follows it to load the config. Always use absolute paths.
sudo rm /etc/nginx/sites-enabled/dustyserver
Disable a site. Removes the symlink only — the config in sites-available/ is preserved. After a reload, the site is offline.
ls -la /etc/nginx/sites-enabled/
List all enabled sites and their symlink targets. Use this to confirm which configs are active and that symlinks point to the right files.
readlink -f /etc/nginx/sites-enabled/dustyserver
Print the absolute path the symlink resolves to. Use this to debug a broken symlink — if it shows a path that doesn't exist, the symlink is broken.
Logs
sudo tail -f /var/log/nginx/access.log
Follow the access log live — every request as it arrives. Shows client IP, HTTP method, URL, status code, and response size.
sudo tail -f /var/log/nginx/error.log
Follow the error log live. Shows config errors at startup, permission denials, upstream failures, and all other problems. Check this when something isn't working.
sudo grep "dustyserver.co.in" /var/log/nginx/access.log | tail -20
Filter access log to show only requests for a specific domain. Useful when multiple sites share the same access.log.
sudo journalctl -u nginx -f
Follow Nginx's systemd logs — shows start/stop events and critical errors that may not appear in error.log.
Diagnostics
sudo ss -tlnp | grep :80
Show which process is listening on port 80. If something other than Nginx is shown, port 80 is occupied and Nginx won't be able to start.
curl -H "Host: dustyserver.co.in" http://localhost/
Test a specific server block locally by spoofing the Host header. Nginx routes by Host header — this simulates a real domain request without needing DNS.
curl -I http://dustyserver.co.in/
Fetch only the HTTP response headers — shows status code, Content-Type, Server header, and cache headers. Useful for checking redirects and MIME types without downloading the body.
nginx -v
Print the Nginx version number. Use nginx -V (capital V) to also see compile-time modules and flags.
01 — What went wrong
Blockers hit while setting up Nginx on spserver
⚠ Blocker 1
Site still showing "Welcome to nginx" after adding own server block
Wrote the dustyserver config in sites-available, created the symlink, reloaded Nginx — but visiting dustyserver.co.in still showed the default Nginx welcome page. The new server block appeared to do nothing.
✓ Fix
The default site's server block was intercepting requests before dustyserver's block
The default server block in /etc/nginx/sites-enabled/default uses server_name _; — the underscore is a catch-all that matches any domain not handled by another server block. When Nginx gets a request for dustyserver.co.in, it compares it against all server_name directives. Since dustyserver was the new block but default was also loaded, the default was winning (alphabetically first in some cases, or due to the default_server flag). Fix: sudo rm /etc/nginx/sites-enabled/default then sudo nginx -t && sudo systemctl reload nginx. The site immediately started serving the correct content.
⚠ Blocker 2
nginx -t passed but the config was silently not loaded — symlink was broken
Created the symlink with a relative path: sudo ln -s ../sites-available/dustyserver /etc/nginx/sites-enabled/dustyserver. The nginx -t test passed (Nginx only checks files it can find — a missing include isn't an error), but the dustyserver site wasn't working.
✓ Fix
Symlinks must use absolute paths — relative paths resolve from the wrong directory
Confirmed with readlink -f /etc/nginx/sites-enabled/dustyserver — it showed a path like /home/sipu/../sites-available/dustyserver which doesn't exist. Deleted the broken symlink (sudo rm /etc/nginx/sites-enabled/dustyserver) and recreated with the full absolute path: sudo ln -s /etc/nginx/sites-available/dustyserver /etc/nginx/sites-enabled/dustyserver. The config was then loaded correctly on the next nginx -t.
⚠ Blocker 3
403 Forbidden when visiting the site — files not readable by www-data
Nginx was running and the server block was active, but visiting dustyserver.co.in returned 403 Forbidden. The error log showed: "/var/www/dustyserver/index.html" is forbidden (13: Permission denied).
✓ Fix
Files in the document root must be readable by www-data
The files were copied with cp which preserved the original ownership (sipu:sipu). Nginx runs as www-data and had no read permission on those files. Fix: sudo chown -R www-data:www-data /var/www/dustyserver and sudo chmod -R 755 /var/www/dustyserver. The 755 permission gives www-data read and execute access (execute is needed on directories to traverse them). Files should be 644 (read for all, write for owner only). After the permission fix, the site loaded correctly.
⚠ Blocker 4
Nginx failed to start — "Address already in use" on port 80
After an OS restart, Nginx failed to start. sudo systemctl status nginx showed: nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use).
✓ Fix
Another process was already listening on port 80 — identified and stopped it
Ran sudo ss -tlnp | grep :80 to identify what was using port 80. It showed Apache2 had auto-started (it was installed as a dependency of something else). Stopped it: sudo systemctl stop apache2 and disabled it from auto-starting: sudo systemctl disable apache2. Then started Nginx: sudo systemctl start nginx — it bound to port 80 successfully.
01 — Issues and fixes
Common Nginx web server problems and fixes
403 Forbidden
Nginx found the file but can't read it. Check permissions: ls -la /var/www/dustyserver/. Files should be readable by www-data (owner www-data, permissions 644 or 755 for directories). Fix: sudo chown -R www-data:www-data /var/www/dustyserver && sudo chmod -R 755 /var/www/dustyserver. Also check: is the root directory itself traversable? Each parent directory in the path must have execute permission for www-data. Check namei -l /var/www/dustyserver/index.html to see permissions on every directory in the path.
404 Not Found
Nginx is running and the server block is matched, but the requested file doesn't exist at the path constructed from root + $uri. Check: (1) Is the file actually at /var/www/dustyserver/index.html? Run ls /var/www/dustyserver/. (2) Is the root directive correct in the server block? (3) Is the index directive set? Without it, a request for / won't find index.html. (4) Check the error log: sudo tail /var/log/nginx/error.log — it shows the full path Nginx tried to open.
nginx: [emerg] ... — reload or restart fails
Config syntax error. Run sudo nginx -t — it reports the exact file and line. Common causes: missing semicolon at the end of a directive, unmatched braces, wrong directive name (typo), or a server_name value that conflicts with another block. Fix the error, run nginx -t again, confirm "test is successful", then reload. Never run systemctl restart with a failing nginx -t — if Nginx is running, it will stop and fail to start again.
Site still shows default Nginx page after adding server block
The default site is still enabled and intercepting requests. Check: ls /etc/nginx/sites-enabled/ — if default is listed, remove it: sudo rm /etc/nginx/sites-enabled/default then reload. Also check: is the symlink for your site actually in sites-enabled? ls -la /etc/nginx/sites-enabled/. If the symlink is missing or broken, the config isn't loaded.
Config file exists but nginx -t doesn't mention it
The config is in sites-available but not symlinked into sites-enabled — Nginx ignores sites-available entirely, it only reads sites-enabled. Or the symlink is broken. Check: readlink -f /etc/nginx/sites-enabled/dustyserver — if the output path doesn't exist, the symlink is broken. Delete and recreate with absolute paths: sudo ln -s /etc/nginx/sites-available/dustyserver /etc/nginx/sites-enabled/dustyserver.
Address already in use — port 80 occupied
Another process is listening on port 80. Find it: sudo ss -tlnp | grep :80 — the last column shows the process name and PID. Common culprits: Apache2, another Nginx instance, or a Node.js server. Stop the conflicting service (sudo systemctl stop apache2) and disable it from autostart (sudo systemctl disable apache2). Then start Nginx: sudo systemctl start nginx.
How to test a server block without DNS
Nginx routes by the Host HTTP header — not by the URL in the browser. You can fake this with curl: curl -H "Host: dustyserver.co.in" http://localhost/. If this returns your site content, the server block is correct and the issue is DNS. If DNS is set up correctly (nslookup dustyserver.co.in resolves to spserver's IP), the domain should work in a browser. DNS propagation can take minutes to 48 hours depending on TTL settings.
