Flask + MySQL Stack

The full spserver-flask 3-container Docker Compose stack — Nginx, Flask, and MySQL running as separate containers on a shared custom network, with persistent MySQL data in a named volume. This is Phase 2 complete.

01 — What & Why
Three containers — one job each

The final Phase 2 stack runs three containers: Nginx as the reverse proxy, Flask as the application, and MySQL as the database. Each does exactly one job. They talk to each other over a custom Docker bridge network called appnet, using service names as hostnames — Docker's internal DNS resolves them automatically.

Single container — everything together
Nginx, Flask, and MySQL all in one container requires a process manager inside (supervisord or similar). You can't restart Flask without restarting Nginx and risking MySQL. The image becomes large and complex. Data lives inside the container and is lost on rebuild. You can't update any one component independently.
Three containers — one job each
Each container has a single, well-defined responsibility. Nginx handles routing and SSL offload. Flask handles application logic. MySQL handles data. You can rebuild Flask after a code change without touching MySQL or its data. Nginx can be reconfigured with a nginx -s reload inside the container. This is the separation of concerns principle applied to infrastructure.
ℹ This guide is the culmination of Phase 2. It brings together the Dockerfile, Docker Compose, Flask app, Nginx, and networking knowledge from the previous guides into a single working production-like stack. The individual pieces are covered in depth in their own guides — this guide focuses on how they fit together and operate as a unit.

03 — expose vs ports
Why Flask and MySQL use expose, not ports

ports and expose are not the same thing. The difference is about who can reach the container — the host machine, or only other containers on the same Docker network.

Propertyports: "8082:80"expose: "5000"
What it does Binds a port on the host to a port inside the container. Traffic from outside the host (or from the host itself) can reach the container. Documents that the container listens on this port. Makes the port reachable from other containers on the same Docker network — not from the host.
Reachable from host Yes — localhost:8082 on the host reaches the container No — nothing on the host can reach port 5000 or 3306
Reachable from other containers Yes (via the host port mapping) Yes — by service name on the shared Docker network
Appears in docker ps PORTS column Yes — 0.0.0.0:8082→80/tcp No — not visible in PORTS column
Used for Nginx — needs to be reachable from the host (host Nginx proxies to it) Flask, MySQL — only other containers on appnet need to reach them. No reason to expose them to the host.
ℹ expose is mostly documentation. On a custom bridge network, containers can reach each other's ports by service name even without expose — Docker bridge networking allows it. The real purpose of expose is documentation: it declares which ports the container is designed to receive traffic on. The enforced restriction is the absence of ports: without a ports mapping, the host cannot reach the port regardless of what expose says.
04 — Networking
Custom network appnet — why and how

Docker Compose creates a default network for each project, but a manually declared custom network gives clearer control and guarantees Docker DNS works reliably for all containers on it.

Default network (no custom network declared)
Compose creates an automatic network named projectname_default. Containers can reach each other by service name on this network too, but it's implicit — nothing in the compose file declares it. If you add services across multiple compose files, they end up on different default networks and cannot reach each other by name.
Custom network appnet (explicit declaration)
Declaring appnet in the networks: block and adding networks: appnet to each service makes the intent explicit. All three containers are on appnet. Docker's embedded DNS registers each service name — nginx, flask, mysql — as a hostname on this network. Any container on appnet can reach any other by service name.
Inside the nginx-proxy container: $ nslookup flask Server: 127.0.0.11 ← Docker's embedded DNS resolver (always this IP) Address: 172.20.0.x ← flask container's IP on appnet $ nslookup mysql Server: 127.0.0.11 Address: 172.20.0.y ← mysql container's IP on appnet This is why proxy_pass uses 'flask', not 'localhost' or an IP: localhost inside the Nginx container = the Nginx container itself flask = resolved by Docker DNS to the Flask container's IP
ℹ When a container is restarted and gets a new internal IP on the bridge network, Docker's DNS record updates automatically. The service name stays constant — code never needs to know IPs.

06 — Persistence & init.sql
Named volume and automatic schema initialisation

A Docker container's filesystem is ephemeral — anything written to it is lost when the container is removed. The mysql-data named volume mounts at /var/lib/mysql inside the MySQL container, keeping all database files outside the container lifecycle.

docker compose down
Stops and removes containers and the Docker network. The mysql-data volume is not touched. All database data survives. Restart with docker compose up -d — MySQL picks up exactly where it left off.
docker compose down -v
Stops and removes containers, network, and all named volumes. The mysql-data volume is permanently deleted. Only use this intentionally for a full reset. There is no undo.

init.sql — the MySQL official image auto-runs any .sql file mounted into /docker-entrypoint-initdb.d/ on first startup, when /var/lib/mysql is empty. This is used to create the schema and seed initial data automatically.

⚠ init.sql only runs once — on first startup. If the mysql-data volume already exists (i.e. the DB was previously initialised), MySQL skips /docker-entrypoint-initdb.d/ entirely. To re-run init.sql after changes: docker compose down -v to wipe the volume, then docker compose up -d. This deletes all data.

02 — Compose file
The full docker-compose.yml — every line explained
flaskapp/docker-compose.yml
services:

  # ── NGINX CONTAINER ─────────────────────────────────────────────
  nginx:
    # nginx:alpine — alpine-based image, much smaller than nginx:latest
    # fewer packages = smaller attack surface, faster pulls
    image: nginx:alpine

    # Fixed container name instead of the random Compose-generated one
    # Makes docker exec, docker logs, and docker inspect easier to use
    container_name: nginx-proxy

    # Restart automatically if the container crashes
    # unless-stopped: respects manual 'docker compose stop' — won't restart after that
    restart: unless-stopped

    # ports — maps host port 8082 to container port 80
    # This is how traffic from outside Docker reaches this container
    # Host Nginx proxies flask.dustyserver.co.in → localhost:8082
    # Nginx inside the container listens on :80
    ports:
      - "8082:80"

    # Mount the nginx config from the host into the container
    # ./nginx/nginx.conf → this file on the host
    # /etc/nginx/conf.d/default.conf → where Nginx looks for site configs
    # Why conf.d/? nginx:alpine includes conf.d/*.conf automatically via nginx.conf include
    # :ro — read-only mount, the container cannot modify the config file
    # Changes on the host take effect after: docker compose exec nginx-proxy nginx -s reload
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro

    # Start flask container before nginx
    # WARNING: depends_on only waits for the container to start, not for Flask to be ready
    # If Flask is slow to start, Nginx may send requests before Flask can handle them
    depends_on:
      - flask

    networks:
      - appnet

  # ── FLASK CONTAINER ─────────────────────────────────────────────
  flask:
    # Build the Flask image from the Dockerfile in the project directory
    # Absolute path used because the compose file may be run from different locations
    build: /home/sipu/projects/flaskapp

    # expose makes port 5000 reachable from other containers on appnet
    # It does NOT create a mapping to the host — the host cannot reach :5000 directly
    # Only the Nginx container (on the same appnet) needs to reach Flask
    expose:
      - "5000"

    # DB connection config passed as environment variables
    # MYSQL_HOST=mysql — 'mysql' is the service name below, resolved by Docker DNS
    # Flask reads these with os.environ.get() in app.py
    environment:
      - MYSQL_HOST=mysql
      - MYSQL_USER=flaskuser
      - MYSQL_PASSWORD=flaskpass
      - MYSQL_DATABASE=flaskdb

    # Start mysql before flask
    # Same caveat: only waits for MySQL container to start, not for MySQL to be ready
    depends_on:
      - mysql

    networks:
      - appnet

    restart: unless-stopped

  # ── MYSQL CONTAINER ─────────────────────────────────────────────
  mysql:
    # Official MySQL 8.0 image — stable, well-maintained
    image: mysql:8.0

    # expose makes :3306 reachable from other containers on appnet
    # No host port mapping — MySQL is not reachable from the host machine
    expose:
      - "3306"

    # MySQL reads these on FIRST startup only (when /var/lib/mysql is empty)
    # On subsequent starts, the existing data is used and these are ignored
    environment:
      - MYSQL_ROOT_PASSWORD=rootsecret
      - MYSQL_DATABASE=flaskdb
      - MYSQL_USER=flaskuser
      - MYSQL_PASSWORD=flaskpass

    volumes:
      # Named volume — persists MySQL data files outside the container lifecycle
      - mysql-data:/var/lib/mysql
      # init.sql — MySQL auto-runs this on first startup to create the schema
      # docker-entrypoint-initdb.d/ is the MySQL image's convention for init scripts
      # Only runs when /var/lib/mysql is empty (i.e. the volume is new)
      - ./mysql/init.sql:/docker-entrypoint-initdb.d/init.sql

    networks:
      - appnet

    restart: unless-stopped

# ── NETWORKS ────────────────────────────────────────────────────
# Declaring appnet explicitly creates a custom bridge network
# All containers on this network can reach each other by service name
# Docker's embedded DNS (127.0.0.11) resolves service names to container IPs
networks:
  appnet:
    driver: bridge

# ── VOLUMES ─────────────────────────────────────────────────────
# Top-level declaration required — without this, docker compose errors on startup
# Docker manages the actual storage path: /var/lib/docker/volumes/flaskapp_mysql-data/
volumes:
  mysql-data:
03 — Nginx config
nginx.conf walkthrough — every directive explained

This file lives at ./nginx/nginx.conf on the host and is mounted read-only into the Nginx container at /etc/nginx/conf.d/default.conf. The Nginx alpine image's main nginx.conf already includes conf.d/*.conf — so this file is automatically loaded.

flaskapp/nginx/nginx.conf
server {
    # Nginx inside the container listens on port 80
    # The docker-compose ports mapping (8082:80) connects host:8082 to this port
    listen 80;

    # Which domain this server block handles
    # Matches the Host header from incoming requests
    server_name flask.dustyserver.co.in;

    # location / matches ALL request paths (/, /api/, /health, etc.)
    # Everything is forwarded to Flask — Nginx serves nothing statically here
    location / {

        # proxy_pass — forward the request to Flask
        # 'flask' is the Docker Compose service name, resolved by Docker DNS (127.0.0.11)
        # Do NOT use localhost — inside this container, localhost = the Nginx container itself
        # Do NOT use an IP — Docker assigns IPs dynamically, they change on restarts
        proxy_pass http://flask:5000;

        # Pass the original Host header to Flask
        # Without this, Flask sees 'flask:5000' as the host instead of 'flask.dustyserver.co.in'
        proxy_set_header Host $host;

        # Pass the real client IP to Flask
        # Without this, Flask sees Nginx's IP (the Nginx container's IP) as the client
        proxy_set_header X-Real-IP $remote_addr;

        # Full chain of IPs the request passed through (Cloudflare → Host Nginx → Nginx container)
        # Useful for logging and rate limiting in Flask
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # Tells Flask whether the original request was HTTP or HTTPS
        # Flask uses this to build correct redirect URLs and set secure cookies
        proxy_set_header X-Forwarded-Proto $scheme;

        # Prevent Nginx from rewriting Location headers in Flask redirect responses
        # Without this, Nginx may change Flask's redirect target URL
        proxy_redirect off;

        # How long Nginx waits for Flask to send back a response
        # 300s is generous — Flask should respond much faster, but long-running
        # endpoints (file uploads, slow DB queries) won't time out prematurely
        proxy_read_timeout 300s;

        # How long Nginx waits to finish sending the request body to Flask
        proxy_send_timeout 300s;
    }
}
ℹ Why :ro on the volume mount? The container should never modify its own config — config is always managed from the host. The :ro flag enforces this: any attempt by a process inside the container to write to the file will be rejected by the OS. To apply a config change: edit the file on the host, then docker compose exec nginx-proxy nginx -s reload — no container restart needed.
ℹ Why /etc/nginx/conf.d/default.conf? The nginx:alpine image's main nginx.conf includes the line include /etc/nginx/conf.d/*.conf;. Any .conf file dropped into conf.d/ is automatically loaded. This is the standard pattern — you can add multiple site configs without touching the main nginx.conf.
04 — MySQL container
MySQL config and automatic schema initialisation

The MySQL container is initialised on first startup by environment variables and a mounted init.sql script. Both are ignored on subsequent starts when the volume already contains data.

VariableValueWhat it does
MYSQL_ROOT_PASSWORD rootsecret Sets the root user password. Required — MySQL won't start without it.
MYSQL_DATABASE flaskdb Creates this database on first start. Must match MYSQL_DATABASE in the Flask environment.
MYSQL_USER flaskuser Creates this user with full privileges on MYSQL_DATABASE. Flask connects as this user.
MYSQL_PASSWORD flaskpass Password for MYSQL_USER. Must match MYSQL_PASSWORD in the Flask environment.
flaskapp/mysql/init.sql — auto-run on first startup
-- This file is mounted at /docker-entrypoint-initdb.d/init.sql
-- MySQL auto-runs it on first startup, after creating the database and user
-- On subsequent starts (volume already has data), this file is ignored

USE flaskdb;

CREATE TABLE IF NOT EXISTS items (
    id       INT AUTO_INCREMENT PRIMARY KEY,
    name     VARCHAR(100) NOT NULL,
    created  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Seed some initial data
INSERT INTO items (name) VALUES
    ('first item'),
    ('second item');
⚠ MySQL only reads environment variables and runs init.sql when /var/lib/mysql is empty — i.e. when mysql-data is a new or wiped volume. If you change env vars or init.sql after the stack has run once, the changes have no effect. To apply them: docker compose down -v to delete the volume, then docker compose up -d. This permanently deletes all data.
05 — Flask container
Flask container — Dockerfile and DB connection

The Flask image is built from the local Dockerfile. The key connector choice and how Flask reads its DB config from environment variables:

requirements.txt
Flask
mysql-connector-python
# mysql-connector-python — pure Python, no system dependencies, installs cleanly in python:slim
# mysqlclient — C extension, requires pkg-config + libmysqlclient-dev → build fails in slim images
app.py — DB config from environment variables
import os
import mysql.connector
from flask import Flask, jsonify

app = Flask(__name__)

DB_CONFIG = {
    # MYSQL_HOST is set to 'mysql' in docker-compose.yml
    # Docker DNS on appnet resolves 'mysql' to the MySQL container's IP
    'host':     os.environ.get('MYSQL_HOST',     'localhost'),
    'port':     3306,
    'database': os.environ.get('MYSQL_DATABASE', 'flaskdb'),
    'user':     os.environ.get('MYSQL_USER',     'flaskuser'),
    'password': os.environ.get('MYSQL_PASSWORD', ''),
}

@app.route('/health')
def health():
    try:
        conn = mysql.connector.connect(**DB_CONFIG)
        conn.close()
        return jsonify({'status': 'ok', 'db': 'reachable'})
    except Exception as e:
        return jsonify({'status': 'error', 'db': str(e)}), 500

if __name__ == '__main__':
    # 0.0.0.0 — listen on all interfaces inside the container
    # Required for the expose + Docker network to work correctly
    app.run(host='0.0.0.0', port=5000, debug=False)

01 — What went wrong
Blockers hit while building the stack
⚠ Blocker 1
Flask crashed on first startup — "Can't connect to MySQL server on 'mysql'"
The first time the stack was started, Flask came up before MySQL finished initialising. depends_on: mysql only waits for the MySQL container to start — not for MySQL to finish its first-time database setup (creating the database, user, and running init.sql). Flask started, immediately tried to connect, got a connection refused, and exited.
✓ Fix
Wait for MySQL logs to show "ready for connections", then restart Flask
Short-term fix: docker compose logs -f mysql — wait for "ready for connections" to appear, then docker compose restart flask. Flask connected successfully on the second attempt. A permanent fix is to add a healthcheck block to the mysql service and change depends_on to condition: service_healthy — Compose then waits for MySQL to pass the healthcheck before starting Flask.
⚠ Blocker 2
pip install failed during build — mysqlclient gcc compilation error
The initial requirements.txt had mysqlclient. The Docker build failed at RUN pip install -r requirements.txt with a gcc compiler error: mysql_config not found. The python:3.11-slim base image doesn't include pkg-config or libmysqlclient-dev.
✓ Fix
Replace mysqlclient with mysql-connector-python
Replaced mysqlclient with mysql-connector-python in requirements.txt. This is a pure-Python MySQL driver — no C compilation, no system dependencies, installs cleanly in slim images. The API is slightly different (import mysql.connector vs import MySQLdb) but fully featured. Rebuilt the image and pip install completed without errors.
⚠ Blocker 3
MySQL data wiped — docker compose down -v used by mistake
During a troubleshooting session, ran docker compose down -v intending to restart cleanly. The -v flag deleted the mysql-data volume — all tables and data were gone. The stack restarted with an empty database.
✓ Fix
Use docker compose down (no -v) for normal restarts
Plain docker compose down stops containers and removes the network but leaves volumes untouched. Only use -v intentionally when a full DB reset is needed. Before any down command, verify: docker volume ls | grep mysql-data. In this stack, init.sql re-creates the schema on the next start after a volume wipe — but any data inserted since initial setup is gone permanently.
⚠ Blocker 4
.bashrc alias for "free" caused division-by-zero error in MOTD on SSH login
After adding a custom alias for free in .bashrc, SSH logins started showing a Python traceback in the MOTD: ZeroDivisionError: integer division or modulo by zero. The MOTD script called free expecting standard output, but the alias intercepted the call and returned reformatted output the script couldn't parse.
✓ Fix
Use /usr/bin/free in scripts — rename the alias to avoid shadowing the system command
Changed the alias name from free to freeh so it no longer shadows the system command. Updated any custom scripts that called free to use the full path /usr/bin/free — full paths bypass aliases entirely. Aliases are expanded in interactive shells but using the full path is more explicit and unambiguous in scripts.
01 — Issues and fixes
Common problems and fixes
Flask exits on startup — MySQL connection refused
MySQL isn't ready yet. depends_on only waits for the container to start, not for MySQL to finish initialising. Fix: (1) docker compose logs mysql | grep "ready for connections" — wait for this message. (2) Once MySQL is ready: docker compose restart flask. Permanent fix: add a healthcheck to the mysql service and use condition: service_healthy in depends_on — Compose then waits for MySQL readiness before starting Flask.
Nginx 502 Bad Gateway — proxy_pass http://flask:5000 failing
Nginx can't reach Flask. Check: (1) Is Flask running? docker compose ps — flask should show "Up". (2) Are both containers on appnet? docker network inspect flaskapp_appnet — both should be listed. (3) Test DNS from inside Nginx: docker compose exec nginx-proxy wget -qO- http://flask:5000/health. (4) Check Nginx logs: docker compose logs nginx. If DNS fails, both services must declare networks: appnet in docker-compose.yml.
proxy_pass http://localhost:5000 not working in nginx.conf
localhost inside the Nginx container refers to the Nginx container itself — not the Flask container. Flask is on a separate container. proxy_pass must use the service name: proxy_pass http://flask:5000;. Docker DNS resolves flask to the Flask container's IP on appnet. This is the most common Nginx container misconfiguration.
Flask can't reach MySQL — "Unknown MySQL server host 'mysql'"
Docker DNS isn't resolving the service name. Check: (1) Is MYSQL_HOST set to mysql? Verify: docker compose exec flask env | grep MYSQL_HOST. (2) Are both flask and mysql in the same networks: appnet block? Services on different networks cannot reach each other by name. (3) Test DNS: docker compose exec flask python -c "import socket; print(socket.gethostbyname('mysql'))".
init.sql changes not taking effect after compose up
init.sql only runs when /var/lib/mysql is empty — i.e. when the mysql-data volume is new. If the volume already has data from a previous run, MySQL skips /docker-entrypoint-initdb.d/ entirely. To re-run init.sql: docker compose down -v to wipe the volume, then docker compose up -d. Warning: this permanently deletes all existing data.
MySQL data gone after docker compose down
Was -v used? docker compose down -v deletes named volumes permanently. Check: docker volume ls | grep mysql — if the volume is missing, the data was deleted. Without a backup this is unrecoverable. Going forward: only use plain docker compose down for normal restarts. Use docker compose down -v only intentionally for a full reset.
nginx.conf change not taking effect
The config is mounted :ro from the host, so changes on the host are immediately visible inside the container — but Nginx still needs to reload to apply them. (1) Test first: docker compose exec nginx-proxy nginx -t. (2) Reload: docker compose exec nginx-proxy nginx -s reload. No container restart needed. If nginx -t shows errors, fix them before reloading — the current working config stays active.
MySQL env var changes not taking effect after restart
MySQL only reads env vars on first start when the volume is empty. The existing volume's data takes precedence. To apply new credentials: (1) docker compose down -v to wipe the volume. (2) docker compose up -d to reinitialise from the new env vars. Warning: this deletes all data. In production, use SQL commands (ALTER USER, CREATE DATABASE) to change config without data loss.
How to confirm which containers are on appnet
Run docker network inspect flaskapp_appnet — the output lists all containers currently connected to the network with their internal IPs and aliases. All three containers (nginx-proxy, flask, mysql) should appear. If one is missing, check that its service definition in docker-compose.yml includes networks: appnet and restart it.
01 — What's next
Future scope — Phase 2 complete, Phase 3 ahead
⟶ Immediate improvements to this stack
Move credentials to a .env file — instead of hardcoding passwords in docker-compose.yml, create a .env file in the project root and add it to .gitignore. Docker Compose auto-loads .env: use MYSQL_PASSWORD=${MYSQL_PASSWORD} in the compose file. Credentials stay out of version control — the single most important security improvement for this stack.
MySQL healthcheck and depends_on condition — add a healthcheck block to the mysql service using mysqladmin ping, and change flask's depends_on to condition: service_healthy. Compose then waits until MySQL passes the healthcheck before starting Flask — eliminating the startup race condition that causes Flask to crash on first boot.
Connection retry in Flask — add a startup retry loop in app.py: try to connect, wait, retry with backoff. This makes Flask robust to transient connection failures without needing the healthcheck-based Compose wait.
MySQL backup strategy — the named volume persists data but lives on spserver's local disk. Set up a cron job: docker compose exec mysql mysqldump -u root -prootsecret flaskdb > /backups/flaskdb-$(date +%F).sql. Run daily, sync dumps to off-site storage via rsync or rclone.
⟶ Phase 3 — Jenkins Deep Dive
Jenkins in Docker — Phase 3 adds Jenkins running as a Docker container with its own data volume. The host Nginx reverse proxy already routes jenkins.dustyserver.co.in to port 8090. Phase 3 covers Jenkins setup, pipeline creation, and CI/CD for the spserver-flask repo.
Automated deployment pipeline — the end state of Phase 3 is a pipeline that watches the spserver-flask GitHub repo, runs tests, builds a new Docker image, and restarts the flask container on every push to main. The Flask + MySQL + Nginx stack built in Phase 2 becomes the deployment target.
